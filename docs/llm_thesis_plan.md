## Problem Statement

Rainier already runs a daily QU100 stock screener (`analysis/stock_screener.py:screen_stocks`) that produces a 3-layer composite ranking: 0.25 money flow + 0.10 sector + 0.65 chart pattern. The top 20 candidates are sent to Discord via `alerts/discord.py:send_stock_candidates` after every scrape. What's missing is an LLM layer that (a) produces a structured per-ticker confidence to combine with the rule-based composite (TODO #11's purpose), and (b) writes a narrative trade thesis the user reads before placing trades. The two outputs come from the same LLM call; building them as separate features would duplicate every input pipeline.

## What Makes This Cool

- **The hard work is already done.** QU100 scraper, 3-layer screener, sector analysis, 12 蔡森 pattern detectors, XGBoost scorer, Plotly charts, X/Twitter API client, Discord notifier, scheduler, `LLMAnalysisRecord` ORM with cost tracking — all already shipped. This feature is glue, not new ground.
- **One LLM call, two outputs.** The same chart + evidence pack produces a structured confidence (combine with rule-based composite for re-ranking) AND a narrative thesis (Discord). Kills TODO #11 by absorbing it.
- **DB-backed cache with idempotency.** `LLMAnalysisRecord` already has prompt/completion tokens and cost tracking. Adding an `input_hash` column with a unique index gives free idempotent inserts: re-running today's scan is a no-op at the DB layer, no LLM calls.
- **Required `patterns_in_chart_not_in_indicators` field.** After 30 days of validation logs, you'll know whether the LLM is finding patterns the 蔡森 detectors miss or just decorating their output. Falsifiable.

## Constraints

- Personal use, no customers. Latency tolerance: a few minutes per morning scan is fine.
- Cost target: well under 3 USD/day with caching.
- Solo dev. Fits in 1-1.5 weekends including tests.
- DB-backed replayability via `LLMAnalysisRecord` + `input_hash`. No file-backed cache.
- Existing module map stays unchanged. New code is one new module (`llm_thesis/`) plus surgical modifications to scheduler, Discord, and the ORM.
- `kaleido==0.2.1` and `litellm>=1.40` are already in `pyproject.toml` — no new dependencies required.

## Premises

1. **Pre-filter is the existing screener output.** Take the top 5 from `screen_stocks()` (already ranked by composite score) — do NOT build a parallel pre-filter. The full top 20 still goes to Discord with rule-based info; only the top 5 get the LLM thesis layer on top.

2. **Evidence pack** = chart image (static PNG produced by a NEW `viz/charts.py:create_static_stock_chart` function, exported via kaleido — there is no existing stock chart function; the existing `create_chart()` is futures-only) + the `StockCandidate` fields produced by `screen_stocks()` (money flow rank, rank delta, capital flow direction, sector, pattern type/direction/status/confidence, entry/SL/target if pattern fired) + composite score. **No X/Twitter data in v1** — the existing X client is synchronous + 16s/request rate-limited (would add ~80s latency for 5 tickers), and the response shape doesn't reliably populate the fields we'd want. Drop it. Reconsider in v2 only if technical-only theses prove too thin.

3. **One LLM call returns both structured confidence AND narrative thesis.** Output is a single `TradeThesis` Pydantic schema with: `verdict` (Literal `setup_long` / `watch` / `no_setup` — **NO `setup_short`** because the screener only selects "Long in" names; allowing setup_short would let the LLM contradict the upstream filter), `setup_quality` (1-10), `llm_confidence` (1-10, used for combined scoring), three short paragraphs (radar / evidence / invalidation), `risks`, `watch_items`, `evidence_used`, `patterns_in_chart_not_in_indicators`. The structured confidence is what TODO #11 asked for; the narrative is what /office-hours asked for. Same call.

4. **Shadow combined scoring (no live re-rank in v1).** Top 20 is sent to Discord in `screen_stocks()` order — the LLM does NOT change the displayed ranking. Internally, for the 5 stocks that get LLM thesis, compute `combined_score = 0.6 * composite_score + 0.4 * (llm_confidence / 10)` and persist it alongside the rule-based rank in `ScreenedStockRecord`. The original TODO #11 weights (0.6/0.4) are unvalidated; running combined as a shadow lets us collect 30 days of data to decide whether to (a) switch to combined ranking, (b) tune the weights with regression on outcomes, or (c) keep rule-only. Reason: the user explicitly does not trust unvalidated weights and wants concrete data before changing the ranking the screener produces. **`StockCandidate` stays frozen and untouched.** Theses are passed as a side `dict[symbol -> TradeThesis]`.

5. **30-day validation discipline, fully DB-backed (no CSV anywhere).** Every screener output row + LLM augmentation + manual outcome lives in a new ORM table `ScreenedStockRecord`. After 30 days, the validation analysis is a SQL query, not a CSV scan. Decide go/no-go on (a) does combined > composite produce better picks (concrete data, not vibes), (b) is `patterns_in_chart_not_in_indicators` substantive enough to keep the discovery channel, and (c) what should the actual weights be.

   Reason: the user explicitly does not want CSV files; everything should be queryable in the existing TimescaleDB. The QU100 raw data in `MoneyFlowSnapshot` stays the immutable source of truth (fixed order matching the QU100 webpage); `ScreenedStockRecord` captures everything we compute on top.

6. **DB-backed idempotent cache, two-tier lookup.** Add `input_hash: String(64)` and `scan_date: Date` columns to `LLMAnalysisRecord`, plus a unique index on `(scan_date, target_symbols, prompt_template, input_hash)`. **Critical: cache lookup happens BEFORE expensive operations.** Two-tier check:
   - Tier 1 (cheap): `SELECT id FROM analysis_results WHERE scan_date = today AND target_symbols = [symbol] AND prompt_template = current_version LIMIT 1`. If hit, skip chart rendering AND skip LLM call entirely. Reruns are truly free.
   - Tier 2 (only on miss): render chart, compute `input_hash = sha256(json_evidence + sha256(image))`, attempt INSERT with `ON CONFLICT DO NOTHING`. If a parallel run already inserted the row (race condition), this is a no-op. Then read back the row to get `id`.

   Codex caught that the original design computed `input_hash` AFTER expensive fetches, defeating the "free reruns" promise. Fixed.

7. **Anthropic prompt cache for the static prefix.** ~90% of tokens (system prompt, output schema, few-shot, style guide) marked cacheable. The 5min TTL covers the 5 back-to-back ticker calls within a single scan run; provides no cross-day savings (~24h gap between scans). LiteLLM ≥1.40 is already in `pyproject.toml`; verify its `cache_control` passthrough on multimodal calls works before committing, fall back to direct `anthropic` SDK if not.

## Cross-Model Perspective

Codex (gpt-5.4, high reasoning) ran during /office-hours and contributed:

- **Coolest version (deferred to v3):** Case-based analog engine. Retrieve 5-10 most similar historical setups for each top-5 name from your own backtest history; the LLM compares "this looks like the winners for these reasons, like the losers for these reasons." Falsifiable memory. The schema and DB-backed cache are designed so this drops in cleanly later.

- **The "tell":** the user's KV-cache comment signals taste for leverage, determinism, replayability — not "AI magic." The design leans into that with prompt-version stamps, evidence hashes, idempotent inserts, and a clean validation log.

- **Where Codex was wrong:** Codex told /office-hours "do not reuse `LLMAnalysisRecord`, it's batch-shaped and too coarse for per-ticker replay." This was based on incomplete information — Codex never read the schema. The actual `LLMAnalysisRecord` has `target_symbols: ARRAY[String(10)]` (single-element list = one ticker), `chart_image_ids`, `recommendation`, `confidence`, `reasoning`, `structured_output: JSONB`, plus full cost tracking (`prompt_tokens`, `completion_tokens`, `total_cost_usd`). It is per-ticker friendly with one trivial schema addition (`input_hash`). Reusing it instead of building a parallel cache table is the right call.

- **Premise-5 (now premise 3) challenge:** Codex argued that "LLM only synthesizes" conflicts with "LLM-discovered patterns." Resolution preserved: the schema has a required `patterns_in_chart_not_in_indicators` field, the prompt explicitly demands the LLM use the chart image as a discovery channel beyond the engineered features. After 30 days, the field's non-empty rate is the falsification signal.

## Approaches Considered

### Approach A: Merge with existing screener + absorb TODO #11 + shadow scoring (RECOMMENDED)

Extend the existing daily flow rather than building a parallel module. The LLM is a reading-aid in v1, not a re-ranker.

- New `src/rainier/llm_thesis/` module with ~5 files (service, schemas, chart_export, prompt, __init__)
- Modify `core/models.py:LLMAnalysisRecord` — add `input_hash` column + unique index for idempotency
- Modify `scheduler/service.py:30-50` — after `screen_stocks()`, run LLM thesis on top 5 (no re-rank), pass theses to Discord, write shadow log
- Modify `alerts/discord.py:send_stock_candidates` — accept optional `theses: dict[str, dict] | None`, emit per-ticker rich message for any candidate whose symbol is in the theses dict

Effort: S (1-1.5 weekends including tests). Risk: Low. Net new code: ~5 files + 3 surgical modifications + 4 test files.

- **Pros:** Reuses 100% of existing pre-filter pipeline; one Discord output not two; absorbs TODO #11 (in shadow mode, with data collection for v2 weight tuning); cost tracking and replayability come from the existing ORM; **`StockCandidate` stays frozen and untouched**; ~50% less new code than the original /office-hours plan.
- **Cons:** Carrying a side `dict[symbol -> thesis]` alongside the candidate list means two values flow through the scheduler hook and Discord call instead of one. Cost is mild; benefit is StockCandidate stays clean.
- **Reuses:** `analysis/stock_screener.py:screen_stocks`, `core/types.py:StockCandidate` (unmodified), `core/models.py:LLMAnalysisRecord`, `apis/x/client.py`, `viz/charts.py`, `alerts/discord.py:send_stock_candidates`, `scheduler/service.py`, LiteLLM transport.

### Approach B: Build parallel module (the original /office-hours plan)

What was on the table before this review caught the existing infrastructure. Now rejected.

- New `src/rainier/llm_thesis/` module with ~10 files including its own pre-filter, file-backed cache, separate Discord renderer
- Two LLM systems live side-by-side: this new one + TODO #11 to be built later
- Two Discord messages every morning (existing top-20 + new top-5-with-thesis)

Effort: M (1.5-2 weekends). Risk: Medium (long-term maintenance debt).

- **Pros:** Less coupling between LLM layer and screener internals.
- **Cons:** Duplicates pre-filter, cache, Discord output. Forces TODO #11 to ship as a third LLM pipeline later. Discord noise is real and immediate.

### Approach C: LLM-as-emitter via SignalEmitter protocol

Implement `LLMSignalEmitter` matching the `SignalEmitter` protocol, plug into backtest engine and `compare_emitters()`.

Effort: M-L. Risk: Medium.

- **Pros:** Could A/B-test thesis-driven trades vs rule/ML-driven trades using the existing comparison harness.
- **Cons:** `Signal` requires `entry_price`, `stop_loss`, `take_profit`. The LLM thesis is qualitative and pulls those values from the underlying pattern (when one fires) or has no entry levels at all (no_setup verdict). Forcing the protocol fit produces fake levels OR requires extending the protocol — both bad. **Does NOT plug into backtest engine "for free"** — the protocol mismatch is real.

## Recommended Approach

**Approach A.** It's smaller, faster to ship, and structurally honest about what already exists. The Codex-recommended file structure from /office-hours becomes a ~5-file module instead of a ~10-file module because the screener, Discord, and DB layers are reused. TODO #11 is folded in: one LLM call produces the structured confidence (for combined scoring) AND the narrative thesis (for Discord), so there is no second LLM pipeline to build later.

If 30-day validation shows combined scoring beats composite scoring on real picks AND `patterns_in_chart_not_in_indicators` is substantive, build the v3 case-based analog engine. If neither, kill the LLM layer and reclaim the daily cost.

## Success Criteria

- LLM thesis runs daily after the morning QU100 scrape. Discord output: existing summary + existing per-candidate detail embeds (~16 messages on a typical morning) PLUS 5 thesis messages stacked on top, in screen_stocks order. Total ~21 morning messages. **Discord ordering is screen_stocks order — no LLM re-rank in v1**; combined_score is computed and stored as `shadow_combined_score` for the day-30 decision but does NOT affect what the user sees.
- Daily cost stays under 1.00 USD per scan on Sonnet 4.6 (~4× headroom over expected 0.26) or 2.50 USD per scan on Opus 4.7 (~2× headroom over expected 1.30), enforced by a hard `--max-usd` kill-switch.
- Every LLM call is idempotent at the DB layer via two-tier cache: cheap Tier 1 lookup before any expensive operation; Tier 2 `INSERT ... ON CONFLICT DO NOTHING` on `(scan_date, target_symbols, prompt_template, input_hash)`. Re-running today's scan is truly zero-cost — no chart render, no LLM call, no DB churn.
- Per-ticker failure does NOT crash the scan: per-ticker try/except, log + continue, and emit a Discord notice "Skipped TICKER: <reason>" so failures are visible.
- DB persistence failures do NOT block Discord: try/except around `persist_screened_stocks` and `update_with_thesis`; 3-strike health check posts Discord warning if the DB layer is failing repeatedly.
- After 30 days: `ScreenedStockRecord` has ~30 morning rows × 5 tickers = ~150 rows with `llm_confidence` populated, plus ~30 × 20 = ~600 rows with `forward_return_5d` populated by the outcome-backfill job. Three metrics computed via SQL: (a) `patterns_in_chart_not_in_indicators_count > 0` rate, (b) **unbiased** P&L correlation: Spearman rank correlation between `forward_return_5d` and (1) `rule_rank` and (2) `would_be_combined_rank`, computed across ALL screened names — not just user-traded ones, (c) marginal lift of combined ranking over rule ranking on the slots that actually matter (top 5).
- A clear go/no-go decision at day 30 based on (a), (b), (c), and whether the user opened the Discord output daily.

## Distribution Plan

Personal use, single user. No external distribution. Deployment is `git pull && uv run rainier db init` (for the `input_hash` column) on the user's machine. The scheduler hook is modified in-place; no new APScheduler job. No CI/CD changes required.
